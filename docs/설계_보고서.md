# 모아타(MOATA) 설계 보고서

Nov 6, 2026 · @주현

모아타는 방향이 비슷한 2\~3명을 빠른 매칭이나 예약 매칭으로 묶어 택시 한 대에 태우고, 각자 탄 구간만큼 요금을 나누는 앱이다(이전 이름: 같이타). 이 보고서는 현재 코드(테스트 101개 통과 기준)의 구조와 처리 흐름을 정리한다. 바꾼 이유와 단계별 계획은 `docs/개선_계획.md`에 있다.

## 1. 개요

승객 앱·기사님 앱(PWA)과 운영 페이지, 그리고 매칭·정산·예측·배차를 맡는 Python 서버 하나로 이루어진다. 카카오·AI 키가 없어도 데모 모드로 전체 흐름이 돈다.

| 구분 | 내용 |
| --- | --- |
| 서버 | Python 3.10+, FastAPI, uvicorn, httpx, SQLite(sqlite3), Google OR-Tools(CP-SAT) |
| 화면 | 프레임워크 없는 HTML·CSS·JavaScript. 승객 앱 `/passenger`, 기사님 앱 `/driver`(둘 다 설치형 PWA), 운영 페이지 `/admin`(PC), 로그인 `/` |
| 지도 | 카카오맵 JavaScript SDK. 실패하거나 키가 없으면 Leaflet + OpenStreetMap |
| 외부 API | 카카오맵 SDK(지도·장소 검색), 카카오모빌리티 길찾기(경로·구간 거리·예상 요금), Gemini·Groq(예측 보정, 매칭 판단, 배차 설명, 운영 요약) |
| 기본 지역 | 삼척시(강원대학교 삼척캠퍼스 주변 데모 지점 15곳) |
| 실행 | `python -m uvicorn app.main:app --reload --host 0.0.0.0 --port 8000` |

외부 키가 없을 때의 동작:

- 카카오 JavaScript 키 없음 → Leaflet 지도와 데모 지점 목록
- 카카오 REST 키 없음 → 직선거리 × 1.3과 요금표로 경로·요금 추정
- AI 키 없음(또는 모두 실패) → 예측은 통계 추정치, 매칭은 OR-Tools 최적 계획, 배차 설명은 규칙 문장

## 2. 시스템 아키텍처

화면은 서버 REST API만 부르고, `service.py`가 매칭·정산·예측·배차·경로 모듈을 조합한다. 카카오맵 SDK만 브라우저가 직접 부르고, 길찾기와 AI는 키가 노출되지 않도록 서버가 부른다.

역할 분담은 **계산은 코드와 OR-Tools, 판단은 AI, 절대 규칙은 코드**다. AI가 무엇을 답하든 동성·정원·시간대·거리·방향·우회 규칙은 코드가 마지막에 다시 확인한다.

> `같이타_설계_다이어그램.pdf`는 이전 구조(같이타) 기준이다. 로그인·배차·탑승 전 안내·AI 매칭은 그림에 없다.

## 4. 계정과 권한

- **학생**: 학교 이메일(`학번@kangwon.ac.kr`, 형식만 확인), 비밀번호(영문·숫자 8자 이상), 닉네임, **성별 필수**(기본값 없음). 성별은 가입 후 본인이 바꿀 수 없고 운영자만 정정한다(진행 중인 요청이 없을 때).
- **기사님**: 별도 가입. **아이디**(영문 소문자·숫자·밑줄 4~20자), 비밀번호, 이름, 차량 번호·차종·색상. 이메일과 성별은 받지 않는다.
- **운영자**: `.env`의 `ADMIN_ID`(기본 `admin`)·`ADMIN_PASSWORD`로 처음 실행할 때 만든다. 아이디로 로그인한다.
- **로그인 화면**: 학생 탭(학교 이메일 → `/passenger`, 운영자 아이디 → `/admin`), 기사님 탭(아이디만, 이메일은 422 → `/driver`).
- **세션**: 앱별 HttpOnly 쿠키(`moata_passenger`·`moata_driver`·`moata_admin`). 같은 브라우저에서 승객 앱과 기사님 앱을 함께 시연할 수 있다. 공통 API는 `X-Moata-App` 헤더로 어느 앱의 쿠키를 쓸지 정한다.
- **권한**: 서버가 엔드포인트마다 역할을 확인한다. 운영 API는 운영자만, 배차·운행·요금 입력은 기사님(자기 운행)만, 요청·수락·안내 확인은 승객(자기 요청)만.

## 5. 전체 프로세스

1. **동승 요청** — 빠른 매칭(지금부터 15분, 마감 5분 뒤) 또는 예약 매칭(40분 뒤~14일 뒤를 2주 달력에서, 시간대 20/30/60분). 출발·도착은 검색, 지도 가운데 핀, 현재 위치로 고른다(위치 권한을 이미 허용했으면 출발지를 현재 위치로 채운다). 인원, 우회 허용(분: 3/5/10/15/20/30), 미매칭 시 처리(혼자 타기/취소). 서버는 우회 분을 단독 소요 시간으로 나눠 우회율로 바꾼다. 2명이면 "동행인도 같은 성별" 확인 필수.
2. **매칭 예측** — 대기 화면이 확률·예상 대기·이유를 보여 준다(9장).
3. **매칭** — 빠른 요청은 들어오는 즉시, 예약 요청은 30초 주기 작업에서. 운영 탭 "AI 자동 매칭"이 꺼져 있으면 "지금 매칭 돌리기"로만 매칭한다(7장).
4. **제안 수락·거절** — 응답 시간(빠른 2분, 예약 30분) 안에 전원이 수락하면 확정. 거절하거나 응답이 없으면 해산되고 같은 상대와는 다시 묶지 않는다.
5. **탑승 전 안내** — 확정되면 승객마다 차량 정보와 신고 방법(탭 4개), 허위 신고 경고를 보여 주고 [확인했어요]를 받는다. 확인 시각(`notice_ack_at`)을 기록한다.
6. **배차** — OR-Tools가 운행 가능한 기사님과 배차가 필요한 그룹을 짝지어 30초짜리 제안을 보낸다. AI가 기사님에게 보여 줄 추천 이유를 쓴다. 거절·시간 초과면 다른 기사님에게 간다.
7. **운행** — 기사님이 정차 지점마다 "○○ 도착"을 누른다. **안내를 확인하지 않은 승객은 탑승 처리할 수 없다**(승객 한 명 단위). "곧 도착 알림"을 보낼 수 있다.
8. **정산** — 기사님이 미터 요금·통행료를 입력하면 승객별 미리보기를 보고 정산 요청을 보낸다. 승객 화면이 정산으로 바뀌고 "송금 완료" 표시를 할 수 있다(실제 결제 없음).
9. **신고** — 운행 중 긴급신고, 탑승 전 동승자 신고, 정산 화면 요금 신고(10장).

화면은 승객 3초, 기사님 2.5초, 운영 3초마다 상태를 다시 불러 바뀐 부분만 다시 그린다.

## 6. 상태 전이

**요청**: `waiting` → `proposed` → `confirmed` → `riding` → `dropped` → `done`. 그 밖에 `cancelled`, `expired`.

**그룹**: `proposed` → `confirmed`(배차 대기, 배차 제안 중) → `riding`(기사님 수락, `progress=-1`은 픽업하러 가는 중) → `completed`. 해산·취소는 `cancelled`.

| 전이 | 조건 |
| --- | --- |
| 요청 `waiting` → 그룹 `proposed` | 매칭(최적화 + AI 판단 + 최종 검증) |
| `proposed` → `confirmed` | 전원 수락. 로그인 없는 데모 동승자는 자동 수락·자동 안내 확인 |
| `proposed` → `cancelled` | 거절, 응답 시간 초과, 마감 |
| `confirmed`(배차 제안) | 운행 가능한 기사님에게 제안. 출발 20분 전 이내면 바로 운행(30초), 그보다 뒤면 예약 배차(2분) |
| `confirmed` → `riding` | 기사님 배차 수락(바로 운행), 또는 예약 배차를 받아 둔 기사님이 운행 시작 |
| 요청 `confirmed` → `riding` | 기사님이 그 승객의 탑승 지점 도착 처리(안내 확인 필수) |
| `riding` → `completed` | 마지막 하차 뒤 요금 입력 |
| 대기 요청 마감 | 희망 시간대 끝 10분 전. 혼자 타기면 단독 그룹(`confirmed`), 취소면 `expired` |

확정 뒤 취소는 출발 30분 전부터 패널티가 쌓이고, 기사님이 오는 중(`riding`)이면 앱에서 취소할 수 없다.

## 7. 매칭: 후보 → OR-Tools → AI 판단 → 검증

```
요청 발생 → [코드] 규칙을 통과한 2·3명 후보 생성(정차 순서 전수 탐색)
          → [OR-Tools] 겹치지 않는 조합 중 가중치 합 최대(최적 계획)
          → [AI] 각 그룹을 지금 제안(propose)할지 기다릴지(wait) 판단 + 이유
          → [코드] 상태 재확인 + 규칙 재검증 → 그룹 제안
```

**1단계: 두 요청이 함께 탈 수 있는지** — `pair_reject_reason`

1. 같은 사용자가 아니고, 서로 거절한 적 없음
2. 좌석 합 ≤ 정원(3명)
3. **같은 성별(항상 적용, 설정으로 끌 수 없음)**
4. 희망 시간대가 5분 이상 겹침
5. 출발지 간 직선거리 ≤ 1,000m
6. 진행 방향 코사인 유사도 ≥ 0.7

```latex
\cos\theta_{ab} = \frac{\vec{v}_a \cdot \vec{v}_b}{\lVert \vec{v}_a \rVert \, \lVert \vec{v}_b \rVert} \ge 0.7
```

**2단계: 정차 순서** — 탑승이 하차보다 먼저이고 중간에 차가 비지 않는 순서(3명이면 60가지)를 모두 보고, 총 거리가 가장 짧으면서 모두의 우회율 제약을 지키는 순서를 고른다.

```latex
d_i^{\text{group}} \le (1+\alpha_i)\, D_i^{\text{solo}}
```

**3단계: OR-Tools CP-SAT 집합 분할** — `optimize.plan_groups`

```latex
\max \sum_{g} w_g x_g \quad \text{s.t.} \quad \sum_{g \ni r} x_g \le 1 \;\; \forall r, \qquad x_g \in \{0, 1\}
```

w\_g = 절감 거리(단독 거리 합 − 그룹 경로 거리) + 150m × 우대 점수. 우대 점수는 마감 임박도(마감 30분 전부터 0→1)와 거절당한 횟수(1회 0.3, 최대 1)를 더한 값이다. 시간 제한은 2초(`OPTIMIZER_TIME_LIMIT_SEC`). 탐욕적 삽입(`run_batch`) 결과도 함께 계산해서, 최적화 결과가 탐욕보다 나쁘거나(시간 제한) OR-Tools를 불러오지 못하면 탐욕 결과를 쓴다. 그래서 결과는 항상 탐욕 이상이다.

**4단계: AI 판단** — `agent.MatchAgent`. 최적 계획과 후보 상위 25개(익명 id `R12`, 종류, 마감까지 남은 분, 거절 횟수, 절감률)를 주고 구조화 응답(JSON)으로 `propose`/`wait`와 이유를 받는다. 도구 호출 여러 번을 한 번의 구조화 응답으로 합쳐 호출 수를 줄였고, 후보 구성이 같으면 90초 동안 같은 판단을 다시 쓴다.

**5단계: 검증과 경보** — 서비스가 AI 결과를 그대로 믿지 않는다.

| 상황 | 처리 | 경보 |
| --- | --- | --- |
| 후보 목록에 없는 그룹, 승객이 겹치는 그룹, 최종 규칙 검증 실패 | 실행하지 않음 | 높음 |
| 마감 5분 이내 승객이 든 그룹을 "기다리기" | 바로 제안으로 바꿈 | 중간 |
| AI 응답 실패 | 최적 계획을 그대로 실행 | 중간 |
| 10분 동안 AI 대체 비율 50% 초과(4회 이상) | — | 높음 |
| AI 선택 절감액(대기 그룹 포함) < 최적 계획의 80% | — | 낮음 |
| AI가 언급하지 않은 최적 계획 그룹 | 그대로 제안 | — |

같은 종류의 열린 경보가 10분 안에 또 생기면 새로 만들지 않고 횟수만 올린다. 모든 판단은 `ai_decisions`에 기록해 운영 페이지 "AI 결정 로그"로 보여 준다. 그룹 저장 직전에는 구성원 성별이 모두 같은지 한 번 더 확인한다(마지막 안전장치).

## 8. 요금 정산

같이 탄 구간은 나눠 내고 혼자 탄 구간은 혼자 내는 구간 분할 방식이다(`fare.split_fare`). 제안 화면의 예상 몫, 기사님 요금 입력 미리보기, 최종 정산이 모두 같은 함수를 쓴다.

```latex
s_i = \sum_{k \in K_i} c_k \cdot \frac{\text{seats}_i}{\sum_{j \in \text{onboard}_k} \text{seats}_j}, \qquad c_k = F \cdot \frac{\ell_k}{L}
```

처리 순서: 구간 나누기 → 통행료(그 구간 탑승자끼리) → 상한 보정(물 채우기) → 10원 단위 내림, 남는 금액은 첫 탑승자 → 예상과 30% 이상 차이면 영수증 확인 메모. 합계가 최종 요금 + 통행료와 다르면 높음 경보를 낸다.

```latex
\text{cap}_i = \text{solo}_i \cdot \frac{F}{F_{\text{est}}} \cdot (1-\beta), \qquad \beta = 0.10
```

검증 예시: 같은 곳에서 3명이 출발해 C 3km, B 6km, A 10km에서 내리고 F = 13,000원이면 A 8,450원, B 3,250원, C 1,300원이다.

## 9. 매칭 예측과 AI 호출

```latex
\lambda' = \lambda p, \qquad P = 1 - (1-p)^{n} \, e^{-\lambda' T}, \qquad E[t \mid t<T] = \frac{1}{\lambda'} - \frac{T e^{-\lambda' T}}{1 - e^{-\lambda' T}}
```

통계 추정치를 먼저 계산하고, AI가 확률을 ±0.25 안에서 조정하며 이유를 쓴다(시간은 0~마감). 빠른/예약 종류도 특징값으로 준다.

AI 호출 계층(`app/llm.py`):

| 상황 | 동작 |
| --- | --- |
| 순서(작업별, `AI_ORDER_*`) | 배차 판단·매칭 판단: Groq → Gemini, 매칭 예상·운영 요약: Gemini → Groq, 모두 실패하면 통계 추정·최적화 결과. 쉬는 상태는 작업끼리 공유 |
| Groq 모델 이름 | 기본 `openai/gpt-oss-120b`. 없는 이름이면 이 키로 쓸 수 있는 모델로 자동 전환, JSON 스키마를 지원하지 않는 모델이면 JSON 모드로 자동 전환 |
| 일시 오류(500·503·504) | 1.5초 뒤 한 번 재시도 → (설정했으면) Gemini 대체 모델 한 번 |
| 한도 초과(429) | 재시도 없이 다음 제공자로. 그 제공자는 60초 쉼(서킷 브레이커) |
| 연속 2번 실패 | 그 제공자 60초 쉼 |
| 타임아웃 | 8초 |
| Groq 생각 강도 | gpt-oss 모델은 `reasoning_effort=low`(`GROQ_REASONING_EFFORT`). 토큰 약 40% 절약, 응답 2배 빠름. 무료 분당 한도에 덜 걸린다 |
| 예측 캐시 | 같은 상황(남은 시간 5분 단위)이면 3분 재사용, 실패도 30초 재사용 |
| 통계 | 제공자별 호출·성공·실패 수, 10분 성공률, 쉬는 시간, 마지막 오류(키 제외)를 운영 페이지에 표시 |

이전 코드가 오류가 많았던 이유: 실패 한 번에 최대 6번 호출, 실패를 캐시하지 않아 30초마다 다시 호출, 캐시 키가 1분마다 바뀜, 타임아웃 20초. 모두 위처럼 고쳤다.

## 10. 탑승 전 안내와 신고

**탑승 전 안내**: 확정되면 차량 번호·차종·기사님 이름(배차 전이면 "기사님을 찾고 있어요"), 함께 타는 사람(익명 A/B/C), 신고 탭 4개 설명, 허위 신고 경고, [확인했어요]. 확인 전 승객은 기사님 앱에 "안내 미확인"으로 보이고 탑승 처리 버튼이 잠긴다.

**신고하기** (`신고하기_화면.md` 기준): 탭 4개 × 카테고리 4개.

| 탭 | 카테고리 |
| --- | --- |
| 긴급·안전 | 사고가 났어요 · 위협·폭력을 당했어요 · 성희롱·성추행 · 몸이 아파요 |
| 운행 | 난폭·과속 운전 · 경로를 벗어났어요 · 기사님이 불친절해요 · 차량 상태가 나빠요 |
| 요금 | 요금이 예상과 달라요 · 미터기를 안 켰어요 · 통행료가 이상해요 · 송금에 문제가 있어요 |
| 동승자 | 동승자가 안 나왔어요 · 불쾌한 말·행동 · 너무 늦게 왔어요 · 정산 금액을 안 보내요 |

- 긴급·안전: 빨간 강조, 경고 박스, `tel:112` 링크 + "운영팀에 긴급 신고 접수". 접수하면 높음 경보.
- 차량 번호·기사님·경로·그룹 상태는 **서버가 그룹 기록에서 채운다**(`snapshot`). 화면이 보낸 값은 쓰지 않는다.
- 위치: GPS(HTTPS에서만) → 없으면 마지막으로 지난 정차 지점 → 없으면 위치 없음. 위치가 없어도 접수는 막지 않는다.
- 동승자 탭: 같은 운행의 다른 동승자만 대상으로 고를 수 있다(한 명이면 자동).
- 같은 사람이 같은 운행에 같은 카테고리를 1분 안에 다시 보내면 기존 신고를 돌려준다(긴급·안전 제외).
- 여는 곳: 운행 중 긴급신고(긴급·안전), 탑승 대기 중 신고하기(동승자), 정산 화면 "요금이 이상해요"·"이의 제기"(요금). 기사님 앱은 운행 중 긴급·안전만.

## 10-1. 신뢰도·포인트(가상 금액)

**공개 정보**: 동승자끼리는 닉네임·성별·신뢰도만 보인다(사용자 id·이메일은 숨김). 기사님 화면은 승객을 익명 A/B/C로 보여 준다. 동승 제안 화면에서 동승자마다 신뢰도 속도계(0 빨강 → 100 초록)를 보여 주고, 신뢰도를 보고 거절할 수 있다. 거절한 사람은 감점되지 않는다.

**신뢰도(0~100, 가입 시 40)**

| 일 | 변화 |
| --- | --- |
| 문제없이 운행을 마침 | +1 (최근 7일 최대 +5) |
| 10번째, 20번째… 운행 | +3 보너스 |
| 20점 미만에서 운행을 마침 | +3 (추가 부담을 감수한 회복, 주간 한도 없음) |
| 출발 30분 이내 취소 | −10 |
| 노쇼(기사님이 탑승 지점 도착을 알리고 3분 뒤 처리) | −20 |
| 운영자가 사실로 확인한 동승자 신고 | −15 (신고만으로는 깎이지 않음) |

**유일한 패널티(20점 미만)**: 합승할 때 내 몫의 15%를 더 내고, 그 금액만큼 동승자 몫을 몫 비율로 깎아 준다(`fare.apply_trust_surcharge`). 더 내는 금액은 혼자 탈 때 요금 × 0.95를 넘지 않아서, 0점이어도 이용은 막지 않고 혼자 타는 것보다는 항상 싸다. 비율은 수락할 때의 신뢰도로 정해 `requests.surcharge_rate`에 기록한다. 모두가 20점 미만이면 나눠 받을 사람이 없어 적용하지 않는다. 합계는 항상 최종 요금과 같다.

**포인트와 예약금**

1. 가입하면 500,000P(`START_POINTS`). 데모 충전 +100,000P.
2. 제안을 수락하면 예상 몫 × 100%(`DEPOSIT_RATIO`)를 예약금으로 잡는다(`hold`). 잔액이 모자라면 수락할 수 없다(402). 그때의 몫을 `base_share`로 기록한다. 자동 수락하는 데모 동승자도 잡는다.
3. 운행이 끝나면 예약금을 풀고(`release`) 실제 몫을 결제한다(`pay`). 별도의 송금 버튼은 없다.
4. 제안이 해산되거나(거절·응답 시간 초과) 그룹이 깨지면 예약금을 돌려준다.
5. 출발 30분 이내 취소나 노쇼로 한 사람이 빠지면, 남은 사람의 새 예상 몫이 `base_share`보다 오른 만큼을 빠진 사람의 예약금에서 보상한다(`comp_out` → `comp_in`, 예약금 한도 안에서). 그래서 남은 사람은 수락 때 몫 그대로 낸다. 남은 예약금은 돌려준다.
6. 모든 이동은 `wallet_tx`, 신뢰도 변화는 `trust_events`에 남고, 승객 앱 내 정보에서 볼 수 있다.

**노쇼 처리**: 다음 정차가 탑승 지점이면 기사님 앱에 "탑승 지점 도착(대기 시작)" 버튼이 있다. 누르면 승객에게 도착 알림이 가고, 3분(`NO_SHOW_WAIT_MIN`) 뒤 "노쇼 처리"가 열린다. 처리하면 그 승객을 빼고 경로를 다시 잡아 계속 운행한다(한 명만 남으면 단독 운행). 마지막 남은 승객은 노쇼로 뺄 수 없다.

**API**: `GET /api/me/wallet`, `POST /api/me/points/topup`, `POST /api/driver/groups/{id}/arrive`, `POST /api/driver/groups/{id}/no-show`, `POST /api/admin/reports/{id}/confirm`.

**DB(스키마 버전 4)**: `users.trust·points·rides_done`, `requests.hold_amount·base_share·surcharge_rate·no_show`, `groups.wait_started_at·wait_request_id`, `reports.confirmed`, 표 `trust_events`, `wallet_tx`. 버전 3 파일은 그 자리에서 칸을 더하고 승객에게 신뢰도 40, 500,000P를 준다.

## 11. 배차

`dispatch_cycle()`은 요청 처리(확정, 기사님 운행 가능 켜기·거절, 운행 종료)와 주기 작업에서 돈다.

운행 가능한 기사님이 앱을 보고 있으면 기사님 앱이 상태를 불러올 때(2.5초마다)도 돈다.

1. 시간이 지난 배차 제안은 그 기사님을 `declined_drivers`에 넣고 정리
2. 배차가 필요한 그룹: 확정, 기사 없음, 제안 없음
   - 출발 20분 전 이내 → **바로 운행할 배차**(수락 시간 30초)
   - 그보다 뒤 → **예약 배차**(수락 시간 2분). 수락하면 기사님만 정해 두고 그룹은 `confirmed`로 남는다. 승객 화면에는 "예약 배차 완료"와 차량 정보가 나온다
3. 운행 가능한 기사님: 스위치 켜짐, 운행 중이 아님, 다른 제안을 받고 있지 않음. 받아 둔 예약과 1시간 안에 겹치는 예약은 보내지 않고, 20분 안에 시작할 예약이 있으면 바로 운행할 배차는 보내지 않는다
4. OR-Tools 배정: 한 기사님 한 그룹, 한 그룹 한 기사님, 배정 수 최대 → 픽업 거리 최소 → 출발 임박 우선. 거절한 기사님에게는 다시 보내지 않는다
5. **AI 배차 판단**: 그룹마다 가까운 후보 기사님 3명과 오늘 운행 수·매출, 마지막 운행 뒤 쉰 시간, 다음 예약까지 남은 시간, 하차 지점에서 다음 예약 출발지까지 거리를 AI(Groq → Gemini)에 주고 기사님을 고르게 한다. 후보 밖이거나 겹치면 실행하지 않고(높음 경보), 최적보다 1.5km 또는 50% 넘게 멀면 최적으로 되돌린다(중간 경보). AI가 실패하면 최적 배정. 고를 후보가 없으면 AI를 부르지 않고, 기사님 앱이 제안을 처음 볼 때 AI가 추천 이유만 다시 쓴다. AI 호출은 DB 잠금 밖에서 하고, 쓰기 전에 그룹·기사님 상태를 다시 확인한다
6. 예약 운행은 기사님 앱 "받아 둔 예약"에서 **운행 시작**을 눌러 시작한다(`riding`). 다른 운행 중에는 시작할 수 없다
7. 확정 뒤 3분 넘게 기사님을 못 찾으면(출발 20분 전 이내) 중간 경보, 예약 운행이 출발 시각이 지나도 시작되지 않으면 중간 경보
8. 운행 가능한 기사님이 모두 거절·무응답한 그룹은 3분 뒤 거절 기록을 지우고 다시 차례로 제안한다(기사님이 적을 때 영영 막히지 않게). 희망 시간대 끝 + 10분이 지나도록 기사님을 못 찾은 확정 그룹은 취소하고 예약금을 돌려준다(요청 상태 `expired`, 경보 `dispatch_failed`)
9. 기사님 앱은 시간이 지난 배차 제안을 바로 정리한다. 실제 GPS가 서비스 지역에서 30km 넘게 떨어져 있으면 배차를 받을 수 없다고 알려 주고, 시연용 "삼척 터미널로 위치 옮기기" 버튼을 보여 준다

기사님 위치는 HTTPS에서 휴대폰 GPS(15초마다)로, 그 밖에는 정차 지점 도착 때마다 그 지점으로 갱신한다.

## 15. 운영·배포·테스트

**주기 작업(30초)**: 마감 처리(제안 해산·단독 전환·만료) → AI 자동 매칭(스위치가 켜져 있을 때) → 배차 → AI 운영 요약(한 시간에 한 번).

**운행 목록**: 지도 바로 아래에 운행 중 / 배차 대기 / 수락 대기 / 최근 완료로 나눈 목록이 있다. 하나를 누르면 지도가 그 운행의 경로·정차 번호·기사님 위치만 크게 보여 주고, 아래에 기사님·차량, 출발 시각, 거리, 요금, 다음 정차, 정차 순서(완료 표시), 승객별 안내 확인·몫·송금 여부, 매칭 방식, 그 운행의 신고가 나온다. 다시 누르거나 "선택 해제"로 전체 보기로 돌아간다. 고른 운행은 새로 고쳐도 유지된다.

**운영 페이지(24시간 모니터링)**: 맨 위 경보(높음은 빨간색, 소리 켜기, 탭 제목에 긴급 수), 신고(긴급 우선, 처리 상태 변경), 지도(대기·그룹·기사님), 지표(대기·수락 대기·확정, 24시간 요청·빠른/예약·매칭 그룹·평균 대기·만료, AI 대체 비율, 경로 추정 대체 비율, 정산 불일치, 열린 경보), 24시간 그래프, 진행 중 그룹과 안내 확인 현황, 매칭 제어, AI 상태·요약·결정 로그, 기사님 현황, 데모 도구.

**PWA**: 승객 앱(`/passenger`)과 기사님 앱(`/driver`)에 각각 매니페스트가 있어 따로 설치된다. 서비스 워커는 화면 파일만 저장하고 API는 항상 네트워크로 보낸다. 휴대폰에서 위치와 설치를 쓰려면 HTTPS가 필요하다.

- 개발 중 HTTPS: `cloudflared tunnel --url http://localhost:8000` 또는 `ngrok http 8000`
- 터널·배포 주소를 카카오 디벨로퍼스 JavaScript SDK 도메인에 등록해야 카카오맵이 뜬다

**배포**: `Dockerfile`로 이미지를 만들고 영구 디스크를 `/data`에 붙인다(`DB_PATH=/data/moata.db`, `COOKIE_SECURE=true`). 주기 작업이 서버 안에서 돌아서 워커는 1개다. 헬스 체크는 `/api/health`. 키는 배포 서비스의 비밀 환경 변수로 넣는다.

**테스트(pytest 101개, 외부 네트워크 없음)**: `tests/conftest.py`가 `.env`의 실제 키를 비우고 시작한다.

## 16. 한계와 다음 단계

| 현재 | 한계 | 다음 단계 |
| --- | --- | --- |
| 후보 비교에 직선거리 × 1.3 | 실제 도로와 다를 수 있음 | 제안 직전 카카오 경로로 우회율 재검증 |
| AI 판단은 한 번의 구조화 응답 | 여러 단계 추론이 필요한 상황은 단순화 | 함수 호출(도구) 여러 번으로 확장 |

| 학교 메일 형식만 확인 | 본인 확인 없음 | 인증 메일, 휴대폰 본인인증 |
| 송금 완료 표시만 | 실제 결제 없음 | PG 결제(사전 승인) |
| 영수증 첨부 버튼만 | 사진 저장 없음 | 업로드 저장 |
| 기사 자격 확인 없음 | 아무나 기사님으로 가입 가능 | 면허·차량 등록증 확인, 운영자 승인 |
| 기사님 쪽 신고는 긴급·안전만 | 승객 노쇼 신고 없음 | 기사님용 신고 탭 |
| 요금표 기본값이 서울 기준 | 강원 지역 요금과 다름 | 삼척 지역 요금표 |

법적으로는 플랫폼중개사업 등록, 위치기반서비스 신고, 동승 안전 기준(동성 동승, 탑승 전 정보 공유, 긴급신고)이 필요하다. 동승 안전 기준은 지금 코드에 기능으로 반영돼 있다.
