# 택시 동승 부킹 앱 기획서

Nov 5, 2026 · @주현

## 1. 서비스 개요

방향이 비슷한 2\~4명이 원하는 시간대에 택시 한 대를 함께 예약하고, 각자 이동한 거리에 비례해 요금을 나눠 내는 동승 부킹 앱이다.

| 항목 | 내용 |
| --- | --- |
| 해결할 문제 | 심야·통학 시간대 택시 잡기 어려움, 혼자 타기엔 부담되는 요금, 동승 후 "누가 얼마 내나" 정산 갈등 |
| 핵심 가치 | 시간대 예약 매칭 · 거리 비례 정산 · 안전한 동승 |
| 1차 타깃 | 같은 캠퍼스·동네에서 비슷한 방향으로 이동하는 대학생, 심야 귀가자 |
| MVP 성공 지표 | 매칭 성공률, 단독 탑승 대비 1인당 절감액, 요금 이의 제기 비율 |

**기획 전제** — 아래 가정이 바뀌면 3장(기능)과 7장(구조)이 달라진다.

- 범위: 학기 프로젝트 수준 MVP. 승객 앱이 중심이고, 기사 쪽은 간이 웹 화면이나 시뮬레이터로 대체한다.
- 지역: 국내. 그래서 지도·길찾기는 국내 API를 쓴다(6장).
- 차량: 중형 택시 기준, 그룹당 승객 최대 3명(설정값).
- 요금: 실제 미터기 요금을 하차 후 입력·확정하고, 탑승 전에는 예상 요금만 보여준다.

## 2. 핵심 사용자 흐름

요청 → 매칭 → 확정 → 탑승 → 하차 → 정산의 6단계이며, 마감 전까지 매칭이 안 되면 단독 탑승 전환이나 취소로 빠진다.

1. **경로 요청** — 지도에서 출발지·도착지를 고른다(키워드 검색 또는 핀 이동). 희망 출발 시간대(예: 22:00\~22:30), 인원, 허용 우회 시간(예: 최대 10분)을 입력하고, 단독 탑승 예상 요금을 함께 보여준다.
2. **매칭 대기** — 서버가 같은 시간대·비슷한 방향의 요청을 묶어 그룹 후보를 만든다. 후보마다 경유 순서, 내 예상 우회 시간, 내 예상 분담 요금을 보여주고 수락/거절을 받는다.
3. **그룹 확정** — 전원이 수락하면 확정된다. 마감 시각(출발 N분 전)까지 미매칭이면 사용자가 미리 고른 옵션(단독 탑승 전환 / 자동 취소)을 적용한다.
4. **배차·탑승** — 출발 전에 택시를 배차한다(MVP는 기사 시뮬레이터). 탑승 순서·위치·좌석을 미리 알리고, 탑승 시 "탑승 확인"을 누른다.
5. **하차** — 각자 내릴 때 "하차 확인"을 누르면 그 시점의 누적 주행거리가 구간 경계로 기록된다.
6. **정산** — 최종 미터기 요금이 확정되면 분배 공식(5장)으로 각자 몫을 계산해 결제하고, 구간별 내역이 담긴 영수증과 상호 평가를 제공한다.

## 3. 기능 명세

MVP는 "예약 → 매칭 → 거리 비례 정산"이 끝까지 한 번 도는 데 필요한 기능만 넣고, 실결제·기사 앱은 2차로 미룬다.

| 영역 | MVP 필수 | 2차 확장 |
| --- | --- | --- |
| 회원·인증 | 소셜 로그인, 휴대폰 본인인증, 성별 입력 | 학교 이메일 인증(캠퍼스 전용 모드), 신뢰 점수 |
| 경로 입력 | 장소 검색·지도 핀, 출발 시간대 선택, 단독 예상 요금 표시 | 즐겨찾기, 반복 예약(매주 같은 시간) |
| 매칭 | 시간대·방향 기반 자동 매칭, 후보 수락/거절, 마감 처리 | 선호 조건(조용히 가기 등), 그룹 채팅 |
| 운행 | 배차(기사 시뮬레이터), 탑승·하차 확인, 동승자 위치 공유 | 기사 앱, 실시간 도착 예정 시간, 경로 이탈 감지 |
| 요금·정산 | 예상 분담액, 미터 요금 입력 후 분배, 정산 내역 | PG 결제·사전 승인, 자동 송금, 영수증 발행 |
| 안전 | 긴급신고 버튼, 탑승 전 동승자·좌석 정보 공지, 신고·차단 | 안심 귀가 공유 링크, 이용 제한 운영 |
| 관리자 | 그룹·요금 조회, 신고 처리 | 통계 대시보드, 분쟁 조정 화면 |

## 4. 매칭 로직

시간대가 겹치고, 방향이 비슷하며, 합쳐 타도 각자의 우회가 허용치 이내인 요청만 한 그룹으로 묶는다. 1\~2분마다 대기 중인 요청을 모아 처리하는 배치 매칭이 MVP에 적당하다.

**후보 필터 (값싼 것부터 순서대로)**

1. 정원·규정 — 인원 합 ≤ 3, 중형 택시면 같은 성별끼리만(8장).
2. 시간대 겹침 — 두 요청의 희망 시간대가 최소 5분 이상 겹쳐야 한다.
3. 출발지 근접 — 출발지 간 직선거리 ≤ 1km(설정값). DB의 공간 인덱스로 거른다.
4. 방향 유사도 — 출발→도착 벡터의 코사인 유사도가 0.7 이상(약 45° 이내)이어야 한다.
5. 우회율 — 그룹 경로에서 각자의 탑승 거리가 단독 직행 거리의 (1 + α)배 이하여야 한다. α는 0.3 정도에서 시작한다.

```latex
\cos\theta_{ab} = \frac{\vec{v}_a \cdot \vec{v}_b}{\lVert \vec{v}_a \rVert \, \lVert \vec{v}_b \rVert} \ge 0.7, \qquad d_i^{\text{group}} \le (1+\alpha)\, D_i^{\text{solo}}
```

**경유 순서 정하기** — 탑승이 항상 하차보다 먼저라는 제약 아래 순서를 전수 탐색한다. 3명이면 6!/2³ = 90가지, 출발지가 같으면 하차 순서 3! = 6가지뿐이라 충분히 빠르다. 총 주행거리가 가장 짧고 5번 조건을 만족하는 순서를 고른다.

**그룹 선택** — 대기 요청을 출발 시각 순으로 보면서, 기존 그룹에 넣었을 때 추가 거리가 가장 작은 곳에 넣고, 넣을 곳이 없으면 새 그룹을 만든다(탐욕적 삽입). 점수는 "단독 거리 합 − 그룹 경로 거리", 즉 절감 거리로 매긴다.

**API 호출 줄이기** — 1\~4번은 좌표 계산만으로 거르고, 남은 소수 후보만 길찾기 API로 실제 도로 거리를 확인한다. 같은 좌표 쌍의 결과는 캐시한다.

더 깊게 보려면 이 문제는 학계에서 Dial-a-Ride Problem(DARP)으로 불린다.

## 5. 거리 비례 요금 분배

추천은 **구간 분할** 방식이다. 경로를 하차 지점마다 구간으로 자르고, 각 구간 요금을 그 구간에 타고 있던 인원수로 똑같이 나눈다. 같이 탄 구간은 나눠 내고, 혼자 탄 구간은 혼자 낸다.

> 그림: 구간 분할 정산 예시 (원본 Claude Doc에만 있음. 아래 계산 예시 표 참고)

0–3km는 셋이, 3–6km는 둘이 나눠 내고, A 혼자 탄 6–10km의 5,200원은 A가 전부 낸다.

```latex
s_i = \sum_{k \in K_i} \frac{c_k}{n_k}, \qquad c_k = F \cdot \frac{\ell_k}{L}
```

F는 최종 미터 요금, L은 총 주행거리, ℓ\_k는 구간 k의 길이, n\_k는 구간 k에 타 있던 인원, K\_i는 내가 타 있던 구간들이다. 각자의 몫을 다 더하면 항상 F가 된다.

**세 가지 방식 비교**

| 방식 | 계산 | 장점 | 단점 |
| --- | --- | --- | --- |
| ① 탑승 거리 비례 | 내 탑승 거리 ÷ 전원 탑승 거리 합 × F | 설명이 가장 쉽다 | 혼자 탄 구간 요금을 먼저 내린 사람이 일부 떠안는다 |
| ② 구간 분할 (추천) | 구간 요금 ÷ 그 구간 탑승 인원, 내가 탄 구간만 합산 | "같이 탄 만큼만 나눔"이라 납득이 쉽다. 기본요금·통행료도 자연스럽게 반영된다 | 하차 시점의 누적 거리를 기록해야 한다 |
| ③ 단독 직행 거리 비례 | 내가 혼자 갔을 때 거리 ÷ 전원의 그 거리 합 × F | 남을 태우느라 돌아간 사람이 손해 보지 않는다 | 실제로 탄 거리와 무관해 경로가 꼬이면 납득이 어렵다 |

**계산 예시** — 같은 곳에서 3명이 출발, C는 3km, B는 6km, A는 10km에서 하차. 최종 미터 요금 F = 13,000원(예시 값).

| 사람 | 탑승 구간 | ① 탑승 거리 비례 | ② 구간 분할 |
| --- | --- | --- | --- |
| A | 0–10km | 6,842원 | 8,450원 |
| B | 0–6km | 4,105원 | 3,250원 |
| C | 0–3km | 2,053원 | 1,300원 |
| 합계 |  | 13,000원 | 13,000원 |

①에서는 A가 혼자 탄 6–10km 구간(5,200원) 중 1,608원을 B와 C가 대신 낸다. ②는 이 문제가 없다.

**보정 규칙**

- 상한 보장 — 각자 몫이 단독 탑승 예상 요금의 90%(최소 할인율 10%, 설정값)를 넘으면 초과분을 나머지 인원에게 비례로 넘긴다. 동승해서 손해 보는 사람이 없게 하는 장치다.
- 통행료 — 통행료가 발생한 구간의 탑승자끼리만 나눈다.
- 미터 스냅샷 — 하차 때마다 미터 금액을 기록할 수 있다면 c\_k를 "미터 금액 차이"로 바꾼다. 시간요금·할증까지 정확히 반영된다. MVP는 GPS 거리 비례로 충분하다.
- 반올림 — 각자 10원 단위로 내림하고, 남는 차액은 대표 결제자에게 붙인다.
- 탑승 전 예상 — 길찾기 API가 주는 구간별 거리와 예상 택시요금에 같은 공식을 적용해 매칭 화면에 미리 보여준다.

## 6. 지도 API 선택

카카오 조합을 추천한다. 다중 경유지 길찾기 한 번으로 구간별 거리와 예상 택시요금이 같이 오기 때문에 5장 공식에 바로 넣을 수 있다. 구글은 국내 자동차 길찾기를 아직 제공하지 않아 제외한다.

| 제공사 | 경유지 경로 | 무료 이용량 | 이 앱에서의 의미 |
| --- | --- | --- | --- |
| [카카오모빌리티](https://developers.kakao.com/docs/latest/en/kakaonavi/rest-api) | 다중 경유지 길찾기, 경유지 최대 30개 | [자동차 길찾기 일 10,000건, 다중 경유지 일 5,000건](https://developers.kakao.com/docs/ko/getting-started/quota) | 응답에 경유지 사이 구간별 거리·시간, 예상 택시요금·통행료가 포함된다 |
| [네이버 클라우드 Maps](https://guide.ncloud-docs.com/docs/maps-overview) | Directions 5(경유지 5개), Directions 15(경유지 15개) | [Directions 5 월 60,000건, Directions 15 월 3,000건(대표 계정 한정)](https://m.ncloud.com/product/applicationService/maps) | 경로 옵션이 다양하다. 3명 그룹이면 경유지 5개로 충분하다 |
| [TMAP](https://openapi.sk.com/products/calc?svcSeq=4&menuSeq=5) | 다중 경유지, 경유지 순서 최적화 | 자동차 경로 일 1,000건, 다중 경유지 30 일 100건, 순서 최적화 일 50건 | 순서 최적화 API가 있지만 무료량이 적어 백업용 |
| 구글 지도 | 국내 자동차 길찾기 미제공 | — | [2026년 2월 정부가 조건부 지도 반출을 허용했지만 이후에도 길찾기는 미지원](https://www.bgr.com/2207179/why-google-maps-doesnt-work-south-korea/) |

**추천 구성**

- 지도 표시·핀 선택: 카카오맵 SDK
- 장소·주소 검색: 카카오 로컬 API(키워드 검색, 좌표↔주소 변환)
- 경로·구간 거리·예상 요금: 카카오모빌리티 다중 경유지 길찾기
- 경유 순서: 4장의 전수 탐색을 서버에서 직접 계산(외부 최적화 API 불필요)

**주의할 점**

- [2026년 7월 21일부터 카카오맵 API 무료 쿼터는 개발자 계정당 처음 활성화한 앱 하나에만 준다](https://devtalk.kakao.com/t/api-notice-on-new-kakao-map-api-features-and-free-quota-policy/150222). 팀 프로젝트면 키를 한 계정에서 발급해 공유하는 편이 낫다.
- 같은 좌표 쌍의 길찾기 결과는 캐시해서 쿼터를 아낀다. 단, 경로 결과를 오래 저장해 재사용해도 되는지는 이용약관을 확인한다.
- 쿼터·요금은 바뀔 수 있으니 개발 시작 시점에 콘솔에서 다시 확인한다.

## 7. 시스템 구조와 데이터 모델

앱은 지도 표시와 장소 검색만 하고, 매칭·정산·길찾기 호출은 서버가 맡는다. 길찾기 REST 키를 앱에 넣지 않아도 되고, 매칭 결과를 한 곳에서 일관되게 관리할 수 있다.

> 그림: 시스템 구조 (원본 Claude Doc에만 있음)

승객 앱과 기사 시뮬레이터는 서버와만 통신하고, 서버가 DB·Redis·길찾기 API를 묶는다.

**기술 스택**

- 앱: Flutter(안드로이드 우선). 웹으로 시작하려면 React + 카카오맵 JavaScript SDK도 가능
- 서버: FastAPI(Python). 매칭·정산 알고리즘을 파이썬으로 바로 실험하고 서비스에 올릴 수 있다
- 저장소: PostgreSQL + PostGIS(반경 검색용 공간 인덱스), Redis(대기열·실시간 위치)
- 실시간: WebSocket(위치 공유), 푸시 알림(매칭 성사·배차)

**주요 테이블**

| 테이블 | 주요 컬럼 | 역할 |
| --- | --- | --- |
| users | id, 이름, 성별, 본인인증 여부, 평점, 패널티 횟수 | 회원과 매칭 필터 조건 |
| ride\_requests | user\_id, 출발·도착 좌표, 희망 시간대(시작·끝), 인원, 허용 우회, 단독 거리·예상 요금, 상태 | 매칭 대상 요청 |
| ride\_groups | 상태(제안→확정→운행→완료), 계획 경로, 총 거리, 예상·최종 요금 | 한 대의 택시에 타는 묶음 |
| group\_members | group\_id, request\_id, 탑승·하차 순서, 수락·탑승·하차 시각, 하차 시 누적 거리 | 구간 경계의 근거 |
| route\_segments | group\_id, 순번, 시작·끝 거리, 탑승 인원, 구간 요금 | 5장 공식의 c\_k, n\_k |
| settlements | group\_id, user\_id, 계산 금액, 보정 후 금액, 결제 상태 | 각자 낼 돈과 내역 |
| reports | 신고자, 대상자, group\_id, 유형, 처리 상태 | 안전 신고·이의 제기 |

## 8. 법·규제 체크리스트

국내에서 택시 동승은 [2022년 1월 28일부터 플랫폼 앱을 통한 경우에만 합법](https://news.seoul.go.kr/traffic/archives/507259)이고, 앱이 갖춰야 할 안전 기준이 정해져 있다. MVP가 시뮬레이션이라도 이 기준을 기능으로 넣어 두면 실서비스로 넘어가기 쉽다.

| 항목 | 요구 사항 | 기획 반영 |
| --- | --- | --- |
| 동승 신청 방식 | [승객 모두가 플랫폼으로 신청해야 하고, 본인 확인 후 중개](https://www.smarttoday.co.kr/ko-kr/articles/23506) | 휴대폰 본인인증 필수, 앱 밖에서 합류 불가 |
| 사전 정보 공유 | 동승자의 탑승 시점·위치와 좌석 정보를 탑승 전에 알려야 함 | 매칭 확정 화면에 경유 순서·탑승 위치·좌석 표시 |
| 성별 조건 | 경형·소형·중형 택시는 같은 성별끼리만, 대형 택시는 제한 없음 | 매칭 필터 1번(4장) |
| 긴급신고 | 112 문자 신고 등 긴급신고 기능과 그 사용법을 탑승 전에 안내 | 운행 화면 상단 고정 버튼 |
| 사업 형태 | 기존 사업자가 아니면 플랫폼가맹 면허나 플랫폼중개사업 등록부터 해야 함 | 실서비스 전환 시 필수. 과제 단계에선 해당 없음 |
| 위치정보 | [택시 호출 같은 위치기반 서비스는 방송통신 당국에 사업 신고가 필요](https://www.venturesquare.net/897964/embed)하다. 2025년 10월 개정 법에서는 소관이 방송미디어통신위원회로 바뀌었다 | 위치정보 이용약관·동의 화면, 위치 이력 보관 기간 설정 |
| 개인정보 | 성별·전화번호·이동 경로는 민감도가 높다 | 동승자에게는 닉네임·성별·탑승 위치만 공개, 운행 종료 후 위치 이력 자동 삭제 |
| 결제·송금 | 앱이 돈을 맡아 뒀다가 나눠 보내는 구조는 금융 규제 검토가 필요할 수 있다 | MVP는 정산 금액 안내 + 송금 요청, 2차는 PG사 개별 결제 |

위 내용은 2022년 시행 규칙과 공개 기사 기준이며 법률 자문이 아니다. 실서비스를 준비한다면 출시 전 최신 법령을 확인하고 전문가 검토를 받아야 한다.

## 9. 예외 상황과 운영 정책

동승은 한 명의 변심이 나머지의 요금을 바꾸므로, 취소·노쇼 때 "남은 사람이 손해 보지 않게" 하는 규칙을 먼저 정해 둔다. 아래 수치는 모두 출발값이며 운영하면서 조정한다.

| 상황 | 처리 정책 |
| --- | --- |
| 확정 후 취소 | 출발 30분 전까지 무료. 이후 취소는 본인 예상 분담액의 일부를 위약금으로 받아 남은 인원의 증가분을 메운다 |
| 노쇼 | 택시 도착 후 5분 대기 뒤 노쇼 처리. 위약금 부과, 누적 시 이용 제한 |
| 남은 인원 요금 증가 | 재계산한 몫이 단독 예상 요금을 넘으면 상한까지만 받고, 차액은 위약금이나 쿠폰으로 보전 |
| 하차 확인 누락 | 하차 지점 반경 안에서 동승 차량과 위치가 멀어지면 자동 하차 처리. 기사 화면에서도 하차 처리 가능 |
| 도중 목적지 변경 | 원칙적으로 불가. 동승자 전원 동의 시에만 허용하고 즉시 재계산 |
| 실제 요금이 예상과 크게 다름 | ±30% 이상 차이 나면 영수증 사진을 받고 관리자 검토 후 확정 |
| 결제 실패 | MVP는 대표자 결제 후 개별 송금 요청. 2차에서 카드 사전 승인으로 전환 |
| 요금 이의 제기 | 구간별 내역을 공개하고 하차 후 48시간 안에 이의 신청을 받는다 |
| 안전 신고 | 긴급신고 즉시 112 문자 신고·고객센터 연결, 신고된 사용자는 조사 중 매칭에서 제외 |

## 10. 개발 로드맵과 리스크

8주 기준으로 "경로 입력 → 매칭 → 정산"이 끝까지 도는 데모를 6주차에 먼저 만들고, 남은 기간에 예외 처리와 다듬기를 한다.

1. 1주차 — 요구사항 확정, 와이어프레임, API 키 발급과 쿼터 확인
2. 2\~3주차 — 지도·장소 검색·경로 요청 화면, 길찾기 API 연동, 단독 예상 요금 표시
3. 4\~5주차 — 매칭 서버(필터, 경유 순서 탐색, 탐욕적 삽입)와 가짜 요청 생성기로 100건 단위 테스트
4. 6주차 — 운행 화면(탑승·하차 확인, 위치 공유)과 기사 시뮬레이터. 이 시점에 처음부터 끝까지 도는 데모 완성
5. 7주차 — 구간 분할 정산과 보정 규칙, 취소·노쇼 처리
6. 8주차 — 통합 테스트, 발표용 데모 시나리오 정리

| 리스크 | 영향 | 대응 |
| --- | --- | --- |
| 사용자가 적어 매칭이 안 됨 | 핵심 가치가 안 보인다 | 캠퍼스·심야 시간대로 범위를 좁히고, 데모는 가짜 요청 생성기로 시연 |
| 길찾기 API 쿼터 초과 | 매칭·예상 요금이 멈춘다 | 직선거리 사전 필터와 결과 캐시(4·6장) |
| 실제 미터 요금을 받을 방법이 없음 | 정산 기준이 흔들린다 | 길찾기 API의 예상 택시요금을 F로 쓰는 모드를 둔다 |
| GPS 오차로 하차 거리가 부정확 | 구간 경계가 틀어진다 | 하차 지점을 계획 경로 위의 가장 가까운 점으로 맞춘다 |
| 동승 중 안전 문제·요금 분쟁 | 신뢰가 무너진다 | 8장 안전 기준과 9장 정책을 MVP에 포함 |
