## 2. 기존 규칙에서 바뀌는 점

`CLAUDE.md`의 "지켜야 할 규칙"을 아래처럼 고친다.

| 기존 | 변경 |
| --- | --- |
| 같은 성별(`SAME_GENDER_ONLY`, 끌 수 있음) | 같은 성별 **항상 적용**, 설정 삭제 |
| 자동 매칭은 기본 꺼짐(`AUTO_MATCH=false`), 매칭은 버튼으로만 | AI 매칭 에이전트가 판단하고 코드가 검증 후 실행. 운영 탭 스위치로 끄면 기존처럼 버튼으로만 매칭 |
| Gemini 결과는 보조값(예측에만 사용) | AI는 예측 보정과 **매칭·배차 판단**에 쓴다. 단, 절대 규칙(성별, 좌석, 시간대, 거리, 방향, 우회)은 항상 코드가 최종 검증한다 |
| Gemini 단일 제공자 | Gemini → Grok → 통계 추정 순 대체 |
| 배치 매칭은 탐욕적 삽입(`run_batch`) | 배치 매칭은 OR-Tools CP-SAT로 전체 절감액이 가장 큰 조합을 찾고, 실패하면 `run_batch`로 대체 |

변하지 않는 원칙:
- 외부 API(카카오, Gemini, Grok)가 실패해도 화면이 멈추지 않는다. 항상 추정값이나 기존 알고리즘으로 대체한다.
- 정산 규칙(구간 분할, 상한 보정, 10원 반올림, 합계 = 최종 요금)은 그대로다.
- 키는 `.env`에만 둔다. `.env.example`에는 빈 값만 둔다.

## 3. 단계별 계획

### 1단계. AI 호출 안정화 + Grok 보조

**배경 (현재 코드에서 확인한 문제)**
- 실패 한 번에 호출이 최대 6번 나간다. 주 모델, 1.5초 뒤 재시도, 대체 모델 최대 4개 순이다(`app/predict.py` `GeminiPredictor.predict`).
- 실패 결과는 캐시하지 않는다. 화면은 30초마다 예측을 다시 요청한다(`static/app.js` `render`). 그래서 한도(429)에 걸리면 계속 다시 호출한다.
- 캐시 키에 `int(minutes_left)`가 있어서 1분마다 키가 바뀐다. 대기 승객 수만큼 분당 호출이 늘어난다.
- 타임아웃이 20초라 최악에는 응답이 매우 늦다.

**할 일**
- `LLMProvider` 공통 인터페이스를 만든다. 구현체는 `GeminiProvider`와 `GrokProvider`(xAI, OpenAI 호환 형식, JSON 응답 지정)다.
- 서킷 브레이커: 429나 연속 실패가 나면 해당 제공자를 일정 시간(기본 60초) 쉬고 다음 제공자로 넘어간다.
- 캐시 키에서 남은 시간을 빼거나 5분 단위로 묶는다. 실패도 짧게(예: 30초) 캐시한다.
- 대체 모델은 1개로 줄이고, 타임아웃은 8초로 낮춘다.
- 화면의 "계산 근거"에 실제로 응답한 제공자와 모델을 표시한다.
- 매칭 에이전트(3단계)와 배차 에이전트(4단계)도 같은 인터페이스를 쓴다.

**설정 추가**: `XAI_API_KEY`, `GROK_MODEL`, `AI_TIMEOUT_SEC`, `AI_COOLDOWN_SEC`

**테스트**
- Gemini 429 → Grok 성공
- 둘 다 실패 → 통계 추정치와 오류 이유 표시
- 서킷이 열린 동안에는 해당 제공자를 호출하지 않음
- 같은 상황에서는 캐시된 결과를 사용

**주의**: xAI는 무료 사용량이 거의 없어 크레딧 충전이 필요할 수 있다. 해커톤 전에 확인한다.

### 2단계. 이름 변경 + 디자인 규칙 + 로그인·가입·역할

**이름 변경**
- 화면 문구, `<title>`, 로고, `CLAUDE.md`, `docs/` 문서의 "같이타"를 "모아타(MOATA)"로 바꾼다.

**디자인 규칙 적용**
- 명세의 값을 CSS 변수로 모은다.
  - 색상: 주 색상 `#0B6FE8`, 정보 카드 `#E8F2FF`/`#1E4E8C`, 본문 `#0F172A`, 보조 `#475569`/`#64748B`, 테두리 `#E2E8F0`/`#CBD5E1`, 위험 `#B42318`
  - 글꼴: Noto Sans KR 400/500/700
  - 모서리: 버튼·입력 12–16px, 카드 16–18px, 바텀시트 24px
  - 버튼 높이: 유저 앱 52–54px, 기사님 앱 60–64px
- 지도 위 정보는 바텀시트에 담고, 주요 버튼은 시트 맨 아래에 붙인다. 두 개면 거절 1 : 수락 2 비율로 나눈다.
- 아이콘은 인라인 SVG 선 아이콘만 쓴다. 이모지는 쓰지 않는다.
- 지도 표시 모드
  - `request`: 출발→도착 점선
  - `group`: 파란 실선 + 정차 번호
  - `driver`: 파란 실선 + 차량 아이콘
  - 출발 핀은 파란 원, 도착 핀은 검은 원

**로그인·가입·역할**
- `users`에 `email`, `password_hash`, `role` 컬럼을 추가한다. 기사 정보(차량 번호, 차종·색상, 이름)는 별도 `drivers` 테이블에 둔다.
- 비밀번호는 `hashlib.pbkdf2_hmac`으로 해시한다(새 라이브러리 없음).
- 로그인 유지는 HttpOnly 세션 쿠키로 한다.
- 로그인 화면
  - 학생 탭: 역할에 따라 이동한다. `passenger`는 `/passenger`, `admin`은 `/admin`
  - 기사님 탭: `driver`만 들어갈 수 있고 `/driver`로 이동한다
- 회원가입
  - 학생: 이메일 형식 `@kangwon.ac.kr` 확인, 비밀번호, 닉네임, **성별 필수**
  - 기사님: 별도 가입 화면. 성별은 받지 않는다(매칭 대상 아님)
- 성별은 가입 후 본인이 바꿀 수 없다. 운영자만 정정할 수 있다.
- 서버에서 엔드포인트마다 역할을 확인한다.
  - 운영자만: 수동 매칭, 운영 통계, 경보 처리, AI 자동 매칭 스위치
  - 기사만: 배차 수락, 운행 상태 변경, 요금 입력
  - 승객만: 요청 생성, 제안 수락/거절, 안내 확인
- 데모 계정은 시드 데이터로 만든다(운영자 1, 기사 2, 승객 여러 명 남녀 혼합). 운영자 비밀번호는 `.env`에서 읽는다.

**동성 매칭 고정**
- `SAME_GENDER_ONLY`를 config, `.env.example`, 운영 화면, 설계 보고서에서 지운다.
- 매칭 후보 필터와 예측 통계는 항상 성별을 확인한다.
- 그룹 저장 직전 `service.py`에서 구성원 성별이 모두 같은지 한 번 더 확인한다.
- 좌석 2개 이상 요청 시 "동행인도 같은 성별입니다" 확인 체크를 받는다.

**테스트**
- 기존 테스트에 로그인 픽스처 추가
- 역할별 권한(승객이 운영 API 호출 시 403 등)
- 성별 없이 가입하면 422
- 본인 성별 변경 거부
- 조건이 다 맞아도 남녀는 묶이지 않음

### 3단계. 빠른/예약 매칭 + AI 매칭 에이전트 + 판단 이상 경보

**매칭 종류**

| | 빠른 매칭 | 예약 매칭 |
| --- | --- | --- |
| 시간대 | 지금부터 약 15분 (자동 설정) | 사용자가 미래 시간 선택 (최대 7일 뒤) |
| 매칭 시점 | 요청이 들어오는 즉시 | 주기적으로, 출발 30분 전 그룹 고정 |
| 마감 | 짧게(예: 5분 대기 후 "혼자 탈까요?") | 출발 30분 전 |
| 기사 배차 | 그룹이 확정되면 바로 | 확정 후 미리 배정 |
| 예측 표시 | "5분 안에 동승자를 찾을 확률" | "출발 전까지 묶일 확률" |

- `requests`에 `type` 컬럼(`quick` / `reserved`)을 추가한다.
- 매칭 풀은 하나다. 출발이 가까운 예약 요청과 빠른 요청도 시간대가 겹치면 묶일 수 있다.
- 동승 요청 화면 맨 위에 빠른/예약 전환을 둔다.
- 예약 그룹 고정 후 누군가 취소하면 남은 사람에게 알리고, 다시 매칭할지 혼자 탈지 고르게 한다.

**AI 매칭 에이전트 (하이브리드)**

```
요청 발생
  → [코드] 조건을 모두 통과한 후보 그룹 생성
           (동성, 좌석, 시간대, 거리, 방향, 우회, 최적 정차 순서, 예상 요금)
  → [OR-Tools] 겹치지 않는 그룹 조합 중 전체 절감액이 가장 큰 계획 계산
  → [AI] 그 계획을 지금 실행할지, 일부를 기다릴지 판단 + 이유
  → [코드] 최종 규칙 검증 → 그룹 제안
  → OR-Tools 실패 시 탐욕적 매칭(run_batch), AI 실패 시 최적 계획을 그대로 실행
```

역할 분담: 계산은 OR-Tools, 판단은 AI, 절대 규칙은 코드가 맡는다.

**OR-Tools 그룹 묶기 (CP-SAT 집합 분할)**
- 새 모듈 `app/optimize.py`에 둔다. 입력은 규칙을 통과한 후보 그룹(2명, 3명)과 각 그룹의 절감액이다.
- 변수: 후보 그룹마다 선택 여부(0/1)
- 제약: 한 요청은 최대 한 그룹에만 들어간다. 그룹 좌석 합은 3 이하다(후보 생성 단계에서 이미 걸러짐).
- 목적: 전체 절감액 합 최대. 마감이 가까운 요청과 여러 번 거절당한 요청은 가중치를 더 준다.
- 정차 순서는 기존 `best_order` 전수 탐색 결과를 그대로 쓴다. 3명이면 60가지라 전수 탐색이 정확하고 충분히 빠르다.
- 시간 제한은 기본 2초다. 시간 안에 최적해를 못 찾으면 그때까지 찾은 가장 좋은 해를 쓰고, 해가 없거나 라이브러리를 불러오지 못하면 `run_batch`로 대체한다.
- AI 결정 로그와 운영 탭에 "최적 계획 대비 AI 선택 절감액"을 함께 기록한다. 판단 이상 경보 "기준보다 나쁜 선택"의 기준값으로 쓴다.
- 데모 규모(대기 요청 수십 명)에서는 탐욕 결과와 차이가 작을 수 있다. 시연용으로 탐욕과 최적 결과가 갈리는 데모 데이터를 따로 만들어 둔다.

**설정 추가**: `OPTIMIZER_ENABLED`(기본 true), `OPTIMIZER_TIME_LIMIT_SEC`(기본 2)

**의존성**: `requirements.txt`에 `ortools` 추가. 현재 가상환경(Python 3.14.7)에서 `ortools 9.15.6755`가 설치 가능한 것을 확인했다(2026-11-05, 설치 시험만 함).

- 에이전트 도구(함수 호출)
  - `list_candidates(request_id)`: 후보 그룹, 우회율, 1인 요금, 절감액
  - `evaluate_group(request_ids)`: 조합의 규칙 통과 여부와 요금
  - `decide(group | wait, reason)`: 최종 결정
- AI가 맡는 판단 예시
  - 지금 2명으로 묶을지, 같은 방향 요청을 조금 더 기다릴지
  - 출발이 가까운 예약 요청에 빠른 요청을 붙일지
  - 마감이 가까운 사람과 여러 번 거절당한 사람을 먼저 챙기기
- 실행 시점: 빠른 요청이 들어올 때(이벤트), 예약 요청은 주기 작업 때
- 운영 탭 "AI 자동 매칭" 스위치. 기본값은 켜짐이고, 끄면 기존처럼 "지금 매칭 돌리기"로만 매칭한다.
- 모든 판단을 `ai_decisions` 테이블에 기록한다(입력 후보, 선택, 이유, 제공자, 검증 결과). 운영 탭에 결정 로그로 보여 준다.

**판단 이상 경보**

| 경보 | 조건 | 심각도 |
| --- | --- | --- |
| 규칙 위반 제안 | AI가 고른 그룹이 코드 검증에서 떨어짐. 해당 제안은 실행하지 않음 | 높음 |
| AI 응답 실패 | 모든 AI 제공자가 실패해 기존 알고리즘으로 대체 | 중간 |
| 연속 실패 | 10분 동안 대체 비율 50% 초과 | 높음 |
| 과도한 대기 | "기다리기"만 반복하다 마감이 가까운 요청 발생 | 중간 |
| 기준보다 나쁜 선택 | AI 선택의 절감액이 기존 알고리즘 결과보다 크게 낮음 | 낮음 |

- `alerts` 테이블: 시각, 종류, 심각도, 관련 요청·그룹, AI 이유, 확인 여부
- 운영 탭 맨 위에 경보 목록을 둔다. 높음은 빨간색과 소리 알림. 긴급 신고와 같은 영역에 표시한다.
- 운영자는 경보를 확인 처리하거나 그 자리에서 수동 매칭을 다시 돌릴 수 있다.

**테스트**: 가짜 AI 제공자로 다음을 확인한다.
- 정상 선택 → 그룹 생성
- 규칙 위반 선택 → 실행 안 됨 + 높음 경보
- AI 실패 → 기존 알고리즘 결과 + 중간 경보
- 스위치 꺼짐 → 자동 실행 안 됨
- 빠른/예약 요청이 시간대가 겹치면 함께 묶임
- OR-Tools 결과의 전체 절감액이 탐욕 결과보다 크거나 같음
- 탐욕이 손해를 보는 사례(A·B를 먼저 묶으면 C·D가 남는 경우)에서 OR-Tools가 더 나은 조합을 찾음
- 한 요청이 두 그룹에 들어가지 않음
- OR-Tools를 불러오지 못하거나 시간이 초과되면 `run_batch` 결과로 대체

### 4단계. 탑승 전 안내 + 기사님 앱 + 배차 에이전트

**탑승 전 신고 안내** (상태: 확정 → **안내 확인** → 운행)
- 그룹 확정 후 승객마다 안내 화면을 띄운다.
  - 차량 번호, 차종·색상, 기사님 이름, 동승자 닉네임 확인
  - 운행 중 화면의 긴급신고 버튼 위치와 신고 4가지 탭
    - 긴급·안전: 112 바로 전화, 운영팀에 위치와 차량 정보 즉시 전달
    - 운행: 난폭 운전, 경로 이탈 등
    - 요금: 요금 차이, 미터기 미사용 등
    - 동승자: 안 나옴, 불쾌한 말·행동 등
  - 허위 신고 시 이용 제한 안내
  - [확인했어요] 버튼
- `requests`에 `notice_ack_at`(확인 시각)을 추가한다.
- 확인 전 승객은 기사님 앱에 "안내 미확인"으로 표시되고, 그 승객의 탑승 처리가 잠긴다. 그룹 전체가 아니라 승객 한 명 단위다.
- 운영 탭에 그룹별 안내 확인 현황을 보여 준다.

**신고하기 화면** (`신고하기_화면.md` 명세 기준)

화면 구성은 명세를 그대로 따른다.
- 운행 중 지도 위 어두운 막 + 위에서 64px 아래부터 시작하는 흰 시트
- 제목 "신고하기", 부제 "목적지로 가는 중 · 차량 번호", 닫기 버튼(44 × 44)
- 탭 4개, 카테고리 2 × 2, 상황 설명(선택, 3줄), 첨부 정보 안내
- 탭을 바꾸면 카테고리는 첫 번째 항목으로 돌아간다

| 탭 | 카테고리 |
| --- | --- |
| 긴급·안전 | 사고가 났어요 · 위협·폭력을 당했어요 · 성희롱·성추행 · 몸이 아파요 |
| 운행 | 난폭·과속 운전 · 경로를 벗어났어요 · 기사님이 불친절해요 · 차량 상태가 나빠요 |
| 요금 | 요금이 예상과 달라요 · 미터기를 안 켰어요 · 통행료가 이상해요 · 송금에 문제가 있어요 |
| 동승자 | 동승자가 안 나왔어요 · 불쾌한 말·행동 · 너무 늦게 왔어요 · 정산 금액을 안 보내요 |

| 항목 | 긴급·안전 | 운행 · 요금 · 동승자 |
| --- | --- | --- |
| 강조 색 | 빨강 `#B42318` | 파랑 `#0B6FE8` |
| 선택된 탭 | 빨간 글씨 + 빨간 밑줄 3px | 파란 글씨 `#0B5BC0` + 파란 밑줄 3px |
| 선택된 카테고리 | 빨간 테두리 2px + `#FEF3F2` 배경 | 파란 테두리 2px + `#F3F8FF` 배경 |
| 경고 박스 | 있음(`#FEF3F2` 배경, `#FECDCA` 테두리, `#7A271A` 글씨) | 없음 |
| 하단 버튼 | **112에 바로 전화**(`<a href="tel:112">`) + 운영팀에 긴급 신고 접수 | **신고 접수** |

명세와 다르게 하거나 보탤 점:

1. **신고 데이터를 칸별로 나눈다.** 명세는 `note`에 카테고리와 설명을 함께 담지만, 운영 탭에서 카테고리별로 걸러 보고 통계를 내려면 칸을 나눠야 한다. `reports` 테이블을 아래처럼 넓힌다.

   | 컬럼 | 내용 |
   | --- | --- |
   | `kind` | 탭: `emergency` / `driving` / `fare` / `companion` (기존 `report`, `dispute`는 각각 `driving`, `fare`로 옮김) |
   | `category` | 카테고리 코드(예: `accident`, `route_deviation`, `no_show`) |
   | `note` | 상황 설명(선택, 500자) |
   | `reporter_id` | 신고한 사용자(로그인 세션에서 읽음) |
   | `target_request_id` | 동승자 탭에서 신고 대상 동승자 |
   | `lat`, `lng` | 긴급·안전 탭의 현재 위치 |
   | `snapshot` | 접수 시점의 차량 번호, 기사, 경로, 그룹 상태(JSON) |
   | `status` | `received` → `in_progress` → `resolved` |

2. **첨부 정보는 서버가 채운다.** 차량 번호, 경로, 시각은 화면이 보낸 값을 믿지 않고 서버가 그룹 기록에서 읽어 `snapshot`에 저장한다. 화면은 탭, 카테고리, 설명, 위치만 보낸다.

3. **동승자 탭에는 대상 선택을 넣는다.** 동승자가 2명이면 누구를 신고하는지 알 수 없다. 카테고리 아래에 "누구에 대한 신고인가요?"를 두고 익명 이름(익명 B, 익명 C)으로 고르게 한다. 동승자가 1명이면 자동으로 정한다.

4. **들어가는 곳을 늘린다.** 명세는 운행 중 화면에서만 열리지만, 실제 상황은 그 앞뒤에도 생긴다.

   | 화면 | 열리는 탭 |
   | --- | --- |
   | 운행 중 → 긴급신고 | 긴급·안전 |
   | 탑승 전 안내·기다리는 중 | 동승자("동승자가 안 나왔어요") |
   | 정산 → 요금이 이상해요 · 이의 제기 | 요금 |
   | 정산 완료 후 운행 기록 | 동승자("정산 금액을 안 보내요") |

5. **긴급 신고는 경보와 연결한다.** 긴급·안전 접수는 3단계의 `alerts`에 심각도 높음으로 바로 올라가고, 운영 탭 맨 위에 빨간색과 소리로 표시된다. 운영자는 위치를 지도에서 보고 처리 상태를 바꾼다.

6. **현재 위치는 HTTPS가 필요하다.** 위치를 못 얻으면 마지막으로 지난 정차 지점과 경로를 대신 보낸다. 신고 접수 자체는 막지 않는다.

7. **같은 신고가 겹치지 않게 한다.** 같은 사용자가 같은 그룹에 같은 카테고리를 1분 안에 다시 보내면 새로 만들지 않고 기존 신고를 돌려준다. 단, 긴급·안전은 매번 접수한다.

8. 기사님 쪽 신고(승객 노쇼, 승객 난동)는 이번 범위에서 빼고 이후 과제로 둔다.

접근성은 명세대로 한다. 탭은 `role="tab"` + `aria-selected`, 카테고리는 `role="radio"` + `aria-checked`, 닫기 버튼은 `aria-label="닫기"`, 아이콘은 `aria-hidden="true"`.

**학생 앱 화면** (명세 기준)
1. 동승 요청 (빠른/예약 전환 추가)
2. 매칭 중 (매칭 확률 원형 그래프, AI 분석 카드, 응답 제공자 표시)
3. 동승 제안 (응답 남은 시간, 정차 순서, 내 예상 몫과 절감액, 거절 1 : 수락 2)
4. **탑승 전 안내** (새 화면)
5. 운행 중 (도착 예정, 차량 정보, 정차 진행, 운행 정보 공유, 긴급신고 → 신고하기 화면)
6. 정산 (구간 막대, 승객별 금액, "송금 완료" 표시, 이의 제기)

**기사님 앱 화면** (글씨와 버튼을 더 크게)
1. 배차 요청 (운행 가능 스위치, 수락 남은 시간, 요약 3칸, 정차 지점)
2. 운행 (다음 정차, 내릴 승객 강조, 안내 미확인 표시, "○○ 도착" 버튼, 곧 도착 알림)
3. 요금 입력 (미터 요금, 통행료, 승객별 정산 미리보기, 예상 요금과 30% 이상 차이 시 영수증 확인 요청 안내, 영수증 첨부 버튼만, 정산 요청 보내기)

**배차 에이전트**
- 기사 상태(대기/운행 중), 현재 위치, 운행 가능 여부를 모델링한다.
- 코드가 배차 가능한 기사-그룹 쌍(픽업 거리, 예상 요금, 마감까지 남은 시간)을 만든다.
- OR-Tools로 기사 여러 명 × 그룹 여러 개를 한 번에 짝짓는다(배정 문제). 목적은 전체 픽업 거리 최소 + 마감 임박 그룹 우선이고, 한 기사는 한 그룹만, 한 그룹은 한 기사만 맡는다.
- AI는 그 배정 결과를 기사에게 보여 줄 제안 문장과 이유로 바꾸고, 예외 상황(예: 곧 운행이 끝나는 기사가 더 가까움)을 판단한다.
- 같은 `LLMProvider`를 쓰고, 실패하면 규칙 점수(픽업 거리, 대기 시간, 요금)로 1순위를 보여 준다.
- AI 호출은 새 그룹이 생기거나 기사가 "추천 받기"를 누를 때만 한다. 폴링마다 부르지 않는다.

**테스트**
- 미확인 승객 탑승 처리 거부, 확인 후 탑승 가능, 확인 시각 기록
- 긴급 신고가 운영 목록 맨 위에 오고 높음 경보가 생김
- 탭에 없는 카테고리로 신고하면 422
- 차량 번호·경로는 화면이 보낸 값이 아니라 서버 기록으로 저장됨
- 동승자 탭에서 같은 그룹이 아닌 사람을 대상으로 고르면 거부
- 같은 신고를 1분 안에 다시 보내면 기존 신고를 돌려줌(긴급·안전은 제외)
- 배차 AI 실패 시 규칙 점수로 대체
- 배차 최적화에서 한 기사가 두 그룹을 맡지 않음, 전체 픽업 거리가 탐욕 배정보다 작거나 같음

### 5단계. PWA + HTTPS

- 승객 앱과 기사 앱에 각각 manifest(이름, 아이콘, 시작 주소)와 service worker를 둔다.
- 휴대폰에서 위치 정보와 service worker를 쓰려면 HTTPS가 필요하다. 개발 중에는 cloudflared나 ngrok 터널을 쓴다.
- 터널 주소와 배포 주소를 카카오 디벨로퍼스 JavaScript SDK 도메인에 등록한다.

### 6단계. 배포 + 운영 24시간 모니터링

**배포**
- Render, Fly.io, Cloud Run 중 하나에 배포한다.
- SQLite 파일은 영구 디스크에 둔다. 재시작해도 데이터가 남아야 한다.
- 헬스 체크 엔드포인트(`/api/health`)를 추가한다.

**운영 페이지 (PC)**
- 명세의 디자인 규칙으로 새로 만든다.
- 맨 위: 긴급 신고와 AI 판단 이상 경보(높음은 빨간색, 소리)
- 지표: 시간대별 요청·매칭·만료 수, 평균 대기 시간, 빠른/예약 비율, AI 제공자별 성공률과 대체 비율, 카카오 추정 경로 대체 비율, 정산 합계 불일치 여부
- AI 결정 로그, 그룹별 안내 확인 현황, AI 자동 매칭 스위치
- 1시간마다 AI가 "이상 징후 요약"을 쓴다. 경보 판정 자체는 규칙으로 한다(비용 통제).
- 이후 PWA 푸시 알림으로 운영자 휴대폰에 경보를 보낸다.

## 5. 위험 요소
